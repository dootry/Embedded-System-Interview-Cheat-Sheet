## 一、C 语言基础

### C01 · volatile 的作用和典型场景 `[泰凌微]`

- **作用**：告诉编译器不做优化，每次访问必须真实读内存 / 寄存器，不缓存到寄存器
- **场景**：
  1. 外设寄存器映射（`#define REG (*(volatile uint32_t*)0x40000000)`）
  2. 中断服务函数修改的全局变量
  3. RTOS 多任务共享的变量
- **追问陷阱**：volatile **不保证原子性**，不能替代互斥锁 / 临界区

> 详见：泰凌微 Q04

### C02 · static 的作用 `[泰凌微]`

从**作用域**和**生命周期**两个维度答：

| 修饰对象 | 作用域 | 生命周期 |
|---|---|---|
| 局部变量 | 仍在函数内 | 变成整个程序运行期（静态区），只初始化一次 |
| 全局变量 | 限定当前 `.c` 文件 | 不变 |
| 函数 | 仅本文件可见 | 不变 |

- 副作用：static 局部变量让函数**不可重入**，多任务下要加锁

> 详见：泰凌微 Q05

### C03 · 指针和数组的区别 `[泰凌微]`

1. 数组名是首地址**常量**，不可修改；指针是**变量**，可改指向
2. `char a[]="abc"` 在栈上分配可写内存；`char *p="abc"` 的 `p` 在栈，`"abc"` 在**只读段**
3. `sizeof(a)` = 数组总长；`sizeof(p)` = 指针大小（4/8）
4. 数组作函数参数会**退化为指针**

> 详见：泰凌微 Q09

### C04 · sizeof 和 strlen 的区别及计算时机 `[A]`

| | `sizeof` | `strlen` |
|---|---|---|
| 本质 | **运算符**（不是函数） | 库函数 |
| 时机 | **编译期**确定（VLA 除外） | **运行期**遍历到 `\0` |
| 是否含 `\0` | 含 | 不含 |
| 作用对象 | 类型 / 变量 / 表达式 | 只能是以 `\0` 结尾的字符串 |
| 能否用于函数 | 不能（除非是返回类型） | 能 |

```c
char arr[] = "abc";   // sizeof=4, strlen=3
char *p   = "abc";    // sizeof=8(64位), strlen=3
void f(char a[10]) { sizeof(a); }  // 结果是 8，已退化为指针
```

> "计算时机"是这道题的题眼：`sizeof` 在编译期就算完了，`strlen` 必须跑起来才知道。

### C05 · 函数指针和指针函数的区别 `[B]`

```c
int (*fp)(int, int);   // 函数指针：fp 指向一个"返回 int、收两个 int"的函数
int* func(int);        // 指针函数：func 返回一个 int*
```

- **辨析口诀看括号**：`(*fp)` 有括号包住 `*` → 是**指针**；`*func()` 没括号 → 返回值是指针
- **函数指针用途**：回调、状态机跳转表、中断向量表、驱动 ops 结构体

```c
typedef struct { void (*init)(void); void (*read)(uint8_t*, int); } sensor_ops_t;
```

### C06 · 全局变量和局部变量的区别 `[B]`

| | 全局变量 | 局部变量 |
|---|---|---|
| 作用域 | 整个程序（跨文件需 `extern`） | 函数 / 块内 |
| 生命周期 | 程序运行全程 | 函数调用期间 |
| 存储位置 | 静态区 `.data` / `.bss` | 栈 |
| 未初始化时 | 默认 0 | **随机值** |

- 全局变量的坑：命名污染、不可重入、多任务下需保护、占用常驻 RAM

### C07 · inline 关键字的作用与适用场景 `[泰凌微]`

**作用**：建议编译器把函数体**直接展开到调用点**，省掉压栈、跳转、出栈的开销。

**适合**：短小、被频繁调用的函数 —— GPIO 读写、位操作、简单 getter。

**不适合**

- 函数体大（代码膨胀，反而拖慢 iCache）
- 含循环、递归（递归无法完全内联）
- 虚函数（运行期才确定调谁，没法静态展开）
- 需要取函数地址的场景

**关键认知：`inline` 只是"建议"，不是命令。** 编译器可以拒绝（函数太大、开了 `-O0`、取了函数地址）。

**和宏对比**

| | `inline` 函数 | 宏 |
|---|---|---|
| 类型检查 | 有 | 无 |
| 参数求值 | 只求值一次 | 可能多次（`SQ(i++)` 是灾难） |
| 调试 | 能打断点 | 展开后难以调试 |
| 作用域 | 遵循 C 规则 | 文本替换，无作用域 |

**工程写法**

```c
// 放头文件里，避免多个 .c 包含时重复定义
static inline uint8_t gpio_read(uint8_t pin) { return (REG >> pin) & 1u; }
```

> 追问预警："`inline` 和 `static inline` 有什么区别？" → 裸 `inline` 在 C99 下不会生成外部定义，多个文件包含会链接失败；`static inline` 每个翻译单元各有一份，最安全，头文件里就用它。

### C08 · static 修饰局部变量与函数可重入的关系 `[泰凌微]`

**现象**：`static` 局部变量放在静态区，函数多次调用共享同一份存储。

**后果：函数不可重入。** 以下三种并发场景都会出错：

1. **多任务**：任务 A 调用到一半被切走，任务 B 再进来，改掉了同一个 static 变量
2. **中断**：主循环正在用这个变量，ISR 又调了一次同一个函数
3. **递归**：自己调自己，内层破坏了外层的值

**可重入函数的条件**

- 只用栈上的局部变量和传入参数
- 不修改全局变量、静态变量
- 不调用不可重入的函数（如 `strtok`、`printf` 的部分实现）
- 不返回指向静态区的指针

**工程改造（句柄式，RTOS 里的标准做法）**

```c
// ✗ 不可重入
float filter(float in) { static float last; last = 0.9f*last + 0.1f*in; return last; }

// ✓ 把状态交给调用者
typedef struct { float last; } filter_t;
float filter(filter_t *f, float in) { f->last = 0.9f*f->last + 0.1f*in; return f->last; }
```

> 这题是 static 的"第二个层次"。只答三种用法是及格，能接到"可重入"上才是面试官想听的。

## 二、内存管理

### M01 · 堆和栈的区别 `[A][B]`

| 维度 | 栈 | 堆 |
|---|---|---|
| 谁管理 | 编译器自动分配释放 | 程序员 `malloc/free` |
| 生长方向 | 向低地址（多数架构） | 向高地址 |
| 大小 | 小，KB 级，链接脚本 / 启动文件里配 | 大，受 RAM 总量限制 |
| 速度 | 快，只移动 SP | 慢，要找空闲块，可能陷入系统调用 |
| 碎片 | 无 | 有外部碎片 |
| 存什么 | 局部变量、函数参数、返回地址、寄存器现场 | 动态分配的对象 |
| 越界后果 | 栈溢出 → HardFault / 跑飞 | 破坏堆管理结构，`free` 时才崩，难查 |

> 嵌入式高频延伸：栈溢出怎么查 → 填魔数（0xDEADBEEF）看水位、`uxTaskGetStackHighWaterMark()`、MPU 栈保护。

### M02 · malloc、calloc 和 kmalloc 的区别 `[A]`

| | 所在环境 | 是否清零 | 特点 |
|---|---|---|---|
| `malloc(size)` | 用户态 | 否 | 内容随机，最常用 |
| `calloc(n, size)` | 用户态 | **是** | 分配 n×size 并清零，适合数组 |
| `kmalloc(size, flag)` | **Linux 内核** | 否 | 从 slab 分配，**物理地址连续**，配套 `kfree` |

- `kmalloc` 的 `flag`：`GFP_KERNEL` 可睡眠（进程上下文），`GFP_ATOMIC` 不可睡眠（中断上下文）
- 内核里还有 `vmalloc`：虚拟连续、物理可不连续，适合大块分配
- 嵌入式 RTOS 里对应的是 `pvPortMalloc`，走 FreeRTOS heap

### M03 · realloc 的原理与注意事项 `[富兰瓦时][泰凌微]`

**原理**

1. 原内存后方空闲够 → **原地扩容**，返回原地址
2. 不够 → 新分配一块、`memcpy` 旧数据、`free` 旧的，**返回新地址**
3. `ptr = NULL` 等价 `malloc`；`new_size = 0` 等价 `free`

**四个坑**

```c
// 坑 1：直接覆盖原指针，失败就丢指针 → 内存泄漏
ptr = realloc(ptr, n);          // ✗
void *tmp = realloc(ptr, n);    // ✓
if (tmp) ptr = tmp;

// 坑 2：扩容出来的新区域内容不确定，要自己初始化
// 坑 3：返回值是新地址时，旧指针立即失效，别留悬垂指针
// 坑 4：频繁 realloc 效率差，工程上常用"容量翻倍"策略减少搬家
```

> 详见：泰凌微 Q08

### M04 · memcpy、memmove、strcpy 的区别 `[A][富兰瓦时]`

| | 拷贝依据 | 处理重叠 | 是否检查 `\0` | 边界检查 |
|---|---|---|---|---|
| `memcpy` | 固定 n 字节 | **不处理**，重叠时结果未定义 | 不检查 | 无 |
| `memmove` | 固定 n 字节 | **处理**（判断方向，必要时从后往前拷） | 不检查 | 无 |
| `strcpy` | 直到 `\0` | 不处理 | 会拷贝 `\0` | 无 |

**怎么选**

- 长度已知且内存不重叠 → `memcpy`（最快）
- 源和目标可能重叠（如数组内搬移）→ `memmove`
- 拷贝字符串 → `strncpy` + 手动补 `\0`，或 `snprintf`，别用裸 `strcpy`

> 一句话记忆：`memmove` = `memcpy` + 重叠判断，代价是慢一点点。

### M05 · memcpy 目标空间不足会发生什么，为什么 `[富兰瓦时]`

- **会发生缓冲区溢出**，覆盖目标地址之后的任意内存
- **原因**：`memcpy` 只拿到「目标指针 + 长度」，它**根本不知道目标有多大**，不做任何边界检查，闷头写 n 字节

**后果（按严重程度）**

1. 覆盖相邻变量 → 数据莫名其妙被改
2. 覆盖堆块头部 → 下一次 `free` 时崩溃（现场和真凶相隔很远）
3. 覆盖栈上返回地址 → 函数返回时跳到乱地址，HardFault / 跑飞
4. 覆盖函数指针 / 结构体 → 调用时跳飞

**特点：往往当场不崩，很久之后才崩**，这是这类 bug 最难查的原因。

**防御**：用 `memcpy_s`（带目标长度）、自己封装带长度校验的版本、开 ASan / 栈保护 canary、代码审查时盯紧 `memcpy` 的第三个参数。

### M06 · 什么是内存泄漏、野指针和悬垂指针 `[A]`

| 概念 | 定义 | 典型成因 |
|---|---|---|
| **内存泄漏** | 申请的堆内存没释放，且已失去引用，永远无法回收 | `malloc` 后提前 `return`、指针被覆盖、异常路径漏 `free` |
| **野指针** | 指向**非法 / 未初始化**地址的指针 | 指针定义没初始化、指针越界后的偏移 |
| **悬垂指针** | 指向**已释放内存**的指针（野指针的一种特例） | `free(p)` 后没把 `p` 置 NULL，后续继续用 |

**记忆法**：野指针是「从来没指对过」，悬垂指针是「曾经指对过，但对象没了」。

**规避**：定义即初始化 `= NULL`；`free` 后立刻置 `NULL`；不返回局部变量地址。

### M07 · 如何排查内存泄漏 `[富兰瓦时]`

**嵌入式（无 OS 或 RTOS）**

1. **包装 malloc/free**：记录每次分配的地址、大小、`__FILE__`/`__LINE__`，维护一张表；定时打印未释放条目
2. **看堆水位**：记录当前已分配总量，跑 8 小时 / 24 小时老化，看曲线是否单调上升
3. **二分定位**：注释掉部分模块，看泄漏是否消失，逐步缩小范围
4. **看剩余堆**：FreeRTOS 用 `xPortGetFreeHeapSize()` + `xPortGetMinimumEverFreeHeapSize()`

**Linux 侧**

- Valgrind（`--leak-check=full`）、`mtrace`、AddressSanitizer（LeakSanitizer）
- 静态分析：`cppcheck`、Coverity

### M08 · 内存泄漏后系统会有什么表现 `[富兰瓦时]`

按时间顺序：

1. **短期无感** —— 泄漏速率低时可能几天才显形
2. **可用堆逐渐减少**，`malloc` 开始返回 NULL
3. 代码没判空 → 解引用空指针 → **HardFault**
4. 堆碎片化 → 明明总量够却分配失败，`malloc` 变慢
5. **长时间运行后莫名重启**（看门狗超时，或内存耗尽触发复位）

**最典型的指纹：跑得越久越容易出问题，重启后立刻恢复正常。** 看到这个现象先怀疑泄漏，而不是怀疑硬件。

### M09 · 哪些 C 函数会分配堆内存 `[富兰瓦时]`

**显式分配**

`malloc` / `calloc` / `realloc` / `strdup` / `aligned_alloc` / `memalign`

**隐式分配（容易漏）**

- `asprintf` / `getline`（内部 malloc 缓冲区）
- `pthread_create`（分配线程栈）
- C++ `new` / `new[]`
- 部分 libc 的 `strtok` / `localtime` 实现（返回静态或堆缓冲区，取决于实现）
- `setvbuf` 传入 NULL 时可能内部申请缓冲区

**嵌入式注意**：`printf` 的缓冲区在多数嵌入式 libc 里是**静态分配**（`.bss`），不占堆；但 `asprintf` / `strdup` 一定走堆，实时性要求高的代码里别用。

### M10 · C/C++ 中内存的分配方式 `[B]`

| 区域 | 分配方式 | 释放 | 存放内容 |
|---|---|---|---|
| 静态区 `.data/.bss` | 编译期确定 | 程序结束 | 全局变量、static 变量 |
| 常量区 `.rodata` | 编译期确定 | 程序结束 | 字符串常量、const 全局 |
| 栈 | 函数调用时自动 | 函数返回自动 | 局部变量、参数、返回地址 |
| 堆 | `malloc`/`new` | `free`/`delete` | 动态分配对象 |
| 栈上动态 | `alloca` | 函数返回自动 | 变长数组，慎用 |

C++ 特有：`placement new`（在已有内存上构造对象，常用于内存池）、对象池 / 定长分配器（嵌入式避免碎片的标准做法）。

### M11 · C 程序的内存布局，.bss 和 .data 各存什么 `[泰凌微]`

**从低地址到高地址**

| 段 | 内容 | 占 Flash | 占 RAM |
|---|---|---|---|
| `.text` | 机器指令 | ✔ | 通常不占（XIP 直接跑） |
| `.rodata` | `const` 全局、字符串常量 | ✔ | 不占（或映射只读） |
| `.data` | **已初始化**且初值非 0 的全局 / 静态变量 | ✔（存初值） | ✔ |
| `.bss` | **未初始化或初值为 0** 的全局 / 静态变量 | ✘ | ✔ |
| 堆 heap | `malloc` 动态分配，向上增长 | ✘ | ✔ |
| 栈 stack | 局部变量、参数、返回地址，向下增长 | ✘ | ✔ |

**为什么 .bss 不占 Flash**

如果 1000 个未初始化变量全存进固件，固件里要写 1000 个 0 —— 纯浪费。所以只记录"需要多大"，启动时由启动代码 `memset` 清零。

**由此推出启动流程的两个必做动作**（连到 B01）

1. 把 `.data` 的初值从 Flash **拷贝**到 RAM
2. 把 `.bss` 段**清零**

**面试常问的变形**："一个全局数组 `int buf[1024] = {0}` 占多少 Flash？" → 不占 Flash（放 .bss），只占 4KB RAM。写成 `= {1}` 就会整块搬进 .data，白占 4KB Flash。

## 三、外设与总线

### P01 · I2C 有哪些信号，SCL/SDA 时序规则 `[A][泰凌微]`

**信号**：`SCL` 时钟线 + `SDA` 数据线，**开漏输出，必须外接上拉电阻**（典型 4.7kΩ）

**时序规则**

- 起始 `S`：SCL 高电平期间，SDA **由高变低**
- 停止 `P`：SCL 高电平期间，SDA **由低变高**
- 数据有效性：**SCL 高电平期间 SDA 必须稳定**，只能在 SCL 低电平期间变化
- 每字节 8 bit + 1 位 ACK（接收方拉低 SDA 表示应答）
- 可选：重复起始 `Sr`（读操作切换方向时用）、时钟拉伸（从机拉低 SCL 让主机等）

> 详见：泰凌微 Q10

### P02 · I2C 设备无响应如何调试 `[A][泰凌微]`

按"硬件 → 波形 → 地址 → 复用 → 软件"顺序：

1. **硬件**：上拉电阻是否焊、供电是否正常、SDA/SCL 是否短路到地
2. **波形**：逻辑分析仪抓起始信号有没有出来、地址位对不对、有没有 ACK
3. **地址**：确认 7bit / 8bit 是否搞混（见 P03）
4. **引脚复用**：GPIO 是否正确切到 I2C 功能，是否配成了推挽而不是开漏
5. **软件**：SCL 频率是否超过器件上限、延时是否够、是否漏发停止信号把总线拉死

**总线拉死的救场**：从机在传输中被复位，会一直拉低 SDA。手动发 9 个 SCL 时钟让它把数据吐完，再补一个停止信号即可恢复。

### P03 · I2C 的地址和 R/W 位是什么 `[A]`

- 标准 **7 位地址** + **1 位 R/W**，拼成一个字节：`[A6 A5 A4 A3 A2 A1 A0 | R/W]`
- `R/W = 0` 写，`R/W = 1` 读
- 7 位地址 `0x50` → 写地址 `0xA0`、读地址 `0xA1`（左移一位再补读写位）

**最常见的坑**：驱动 API 通常要 **7 位地址**（`0x50`），你传了 8 位形式（`0xA0`），结果就是全程无 ACK。

**10 位地址**：首字节 `1111 0XX0`（XX 是地址高 2 位），第二字节是低 8 位。

**特殊地址**：`0x00` 广播（general call）、`0x78`–`0x7B` 保留。

### P04 · SPI 有几种模式，Mode 1 的 CPOL/CPHA 和采样边沿 `[A]`

**4 种模式**，由 CPOL × CPHA 组合：

| Mode | CPOL | CPHA | 空闲电平 | 数据移出边沿 | **采样边沿** |
|---|---|---|---|---|---|
| 0 | 0 | 0 | 低 | 上升沿 | 下降沿 |
| **1** | **0** | **1** | **低** | **上升沿** | **下降沿** |
| 2 | 1 | 0 | 高 | 下降沿 | 上升沿 |
| 3 | 1 | 1 | 高 | 下降沿 | 上升沿 |

**Mode 1 答案**：SCK 空闲为**低电平**，数据在**第一个边沿（上升沿）移出**，在**第二个边沿（下降沿）采样**。

**记忆法**：CPHA=0 在第一个边沿采样，CPHA=1 在第二个边沿采样；CPOL 只决定空闲电平和"第一个边沿"是上升还是下降。

> 调 Flash / 传感器不通，90% 是模式选错。Mode 0 和 Mode 3 最常见，Mode 1 相对少见，能被单独点名说明面试官想看你有没有真的踩过。

### P05 · UART 数据帧由哪些部分组成，起始位是什么电平 `[A][泰凌微]`

**帧结构**

```
空闲(高) | 起始位 | D0 D1 ... D7 | 校验位(可选) | 停止位 | 空闲(高)
          1 bit    5–9 bit        0/1 bit      1 / 1.5 / 2 bit
```

- **起始位：低电平**（一个 bit 宽），接收方检测到下降沿即认为帧开始
- **停止位：高电平**
- 数据位通常 8 位，**低位先行（LSB first）**
- 线路空闲时为高电平

> 详见：泰凌微 Q12（乱码排查清单）

### P06 · 什么是串口 `[B]`

- 串行通信接口：数据**逐位**在一根线上传输，对比并口一次传多位
- 嵌入式语境下"串口"通常指 **UART**（异步串行）：只需 TX / RX / GND 三根线，**没有时钟线**，靠双方约定的波特率同步
- 全双工，点对点
- `RS232` / `RS485` / `RS422` 是它的**电气层标准**（电平、抗干扰、传输距离不同），协议层还是 UART 帧

### P07 · PWM 是什么，周期占空比，硬件 PWM 与软件 PWM 的区别 `[A][B][泰凌微]`

**是什么**：脉冲宽度调制。用数字输出（只有高低两态）去等效一个模拟量 —— 改变方波的**占空比**，就改变了负载上的**平均电压 / 平均功率**。

- **周期 T**：一个完整高低电平的总时间，`f = 1/T`
- **占空比**：`高电平时间 / 周期 × 100%`

| | 硬件 PWM | 软件 PWM |
|---|---|---|
| 实现 | 定时器 + 比较寄存器，硬件自动翻转 IO | CPU 在定时器中断里手动翻转 IO |
| CPU 占用 | 进一次配置后完全不管 | 每个边沿都要进中断，通道越多越吃 CPU |
| 精度 / 抖动 | 高，无抖动 | 差，被高优先级任务打断就会抖 |
| 通道数 | 受定时器通道数限制 | 理论上任意多 |
| 适用 | 电机、LED 调光、蜂鸣器 | 临时补一两个通道、成本极简场景 |

> 无线产品几乎必用硬件 PWM —— 软件 PWM 和 BLE 协议栈抢 CPU，抖动会毁掉时序。

### P08 · ADC 是什么 `[B]`

- **模数转换器**，把连续变化的模拟电压转成离散数字量
- 关键参数：
  - **分辨率**：12 bit → `2^12 = 4096` 个刻度
  - **参考电压 Vref**：决定量程，`电压 = ADC值 × Vref / (2^n - 1)`
  - **采样率**：每秒采样次数（SPS）
  - 精度指标：INL / DNL / 失调误差
- **常用场景**：电池电压检测（电阻分压后进 ADC）、NTC 测温、光敏电阻、电位器
- **工程注意**：输入端加 RC 滤波；信号源内阻要小（否则采样电容充不满，读数偏低）；采样前留够建立时间；内部参考还是外部基准要分清

### P09 · GPIO 的输入输出模式，上拉下拉电阻怎么选 `[泰凌微]`

**输出模式**

| 模式 | 行为 | 用途 |
|---|---|---|
| **推挽** Push-Pull | 高电平主动输出高、低电平主动拉低，驱动能力强 | 驱动 LED、普通数字输出 |
| **开漏** Open-Drain | 只能主动拉低，高电平靠外部上拉 | I2C、电平转换、多设备"线与" |

**输入模式**：浮空输入、上拉输入、下拉输入、模拟输入。
原则：**输入引脚不能悬空**（浮空输入电平不确定，输入级来回翻转，既误读又费电）。

**上下拉阻值怎么选（面经原题：大阻值 vs 小阻值）**

这是一道**权衡题**，没有标准答案，要说出取舍：

| | 小阻值（1k–4.7k） | 大阻值（100k–1M） |
|---|---|---|
| 驱动电流 | 大 | 小 |
| 静态功耗 | **高**（3.3V/1k ≈ 3.3mA，电池产品受不了） | 低 |
| 抗干扰 | 强（低阻抗不易被耦合噪声拉偏） | 弱 |
| 上升沿速度 | 快（RC 时间常数小） | 慢（分布电容 + 大电阻 → 边沿变缓） |
| 适用 | 高速信号、强干扰环境、I2C 高速率 | 低功耗待机、按键检测 |

**经验值**

- I2C：100kHz → 4.7kΩ；400kHz → 2.2kΩ
- 按键上拉：10kΩ
- 低功耗产品的休眠期：**干脆把上下拉关掉**，或改配成推挽输出固定电平

> 答这题的关键句："先看速率要求定上限，再看功耗预算定下限，最后留一眼抗干扰余量。"

### P10 · I2C、SPI、UART 各有什么优缺点 `[泰凌微]`

| | I2C | SPI | UART |
|---|---|---|---|
| 线数 | 2（SCL/SDA） | 4（SCK/MOSI/MISO/CS），每多一个从机多一根 CS | 2–3（TX/RX/GND） |
| 同步性 | 同步 | 同步 | **异步**（无时钟线） |
| 双工 | 半双工 | **全双工** | 全双工 |
| 速率 | 100k / 400k / 1M / 3.4M | 几 MHz ~ 上百 MHz | 通常 ≤ 几 Mbps |
| 多设备 | **靠地址寻址**，一条总线挂多个 | 靠**片选**，从机多则线多 | **点对点**，不能挂多设备 |
| 应答机制 | 有 ACK | **无 ACK**，靠协议自己校验 | 无，靠校验位/上层协议 |
| 电平 | 开漏，必须外部上拉 | 推挽，直连 | 单端，需共地 |
| 主要缺点 | 速率低、总线可能被拉死、上拉耗电 | 线多、无应答、无标准协议 | 无时钟易受波特率误差影响、只能点对点 |
| 典型用途 | 传感器、EEPROM、RTC | Flash、屏幕、高速 ADC | 调试口、模组通信、GPS |

**选型口径（面试可以直接说这句）**

> "低速多器件、线要省 → I2C；高速大数据、板内短距 → SPI；跨板、接模组、只要调试 → UART。"

### P11 · 传感器驱动读不到 ID / 通信异常怎么排查 `[泰凌微]`

按"电 → 线 → 波 → 址 → 时序 → 器件状态"六层往下走：

1. **供电**：VDD 是否正常、是否达到器件要求的电压、上电到能通信之间有没有等够稳定时间（很多传感器要 10–100ms）
2. **连线**：SDA/SCL 或 MOSI/MISO 有没有接反、CS 有没有真的拉低、上拉电阻焊没焊
3. **波形**：逻辑分析仪抓一次完整读 ID 的过程，看起始信号、地址、ACK、返回数据
4. **地址**：7 位还是 8 位、ADDR 引脚接高接低的地址偏移对不对
5. **时序**：I2C 速率是否超规格、SPI 的 CPOL/CPHA 是否匹配、CS 建立/保持时间够不够
6. **器件状态**：是否还在复位、是否处于低功耗模式需要先唤醒、寄存器地址是否正确（先读 `WHO_AM_I` 这类固定 ID 寄存器验证链路）

**软件侧常见坑**

- 初始化顺序错（先配置再上电 / 先上电没延时）
- 复位寄存器没写、软复位后没等就访问
- 连续读多个寄存器时用了单字节读，导致地址自动递增行为不符预期
- 读写函数里 CS 忘了拉高，下一帧被吞

> 这题考的是**排查方法论**，不是知识点。按层次说，一层一层砍，比背答案更有说服力。

## 四、DMA 与数据搬运

### D01 · DMA 的作用 `[泰凌微]`

直接内存访问：**外设 ↔ 内存之间直接搬数据，不需要 CPU 逐字节搬运**。

- 解放 CPU，CPU 可以去处理逻辑甚至进低功耗
- 适合大批量、连续的数据：ADC 采样、SPI Flash 读、UART 收包、I2S 音频
- 通常配合"半传输 / 传输完成"中断，做双缓冲乒乓

> 详见：泰凌微 Q22

### D02 · DMA 内存与上层扇区 / 页对齐问题如何定位和解决 `[A]`

**为什么会要求对齐**：DMA 控制器按"传输单位"搬运（SD 卡 512B 扇区、Flash 256B 页、Cache line 32/64B）。地址或长度不是单位的整数倍时，硬件可能只搬整单位部分、或读写到相邻区域。

**典型现象**

- 偶发数据错乱，只有开头或结尾几个字节不对
- 校验和随机失败，重试有时又好
- SD 卡写入后回读内容错位
- 性能突然掉一半（跨 Cache line 触发两次突发）

**定位步骤**

1. 打印 buffer 起始地址，检查 `addr % align == 0`
2. 检查传输长度是不是单位长度的整数倍
3. 逻辑分析仪抓实际传输的字节数，和预期比对
4. 检查是否开了 D-Cache（Cache 与 DMA 一致性是最常见的隐形坑）
5. 看 DMA 描述符本身是否对齐（链表模式下描述符也要对齐）

**解决方案**

| 问题 | 解法 |
|---|---|
| buffer 地址不对齐 | `__attribute__((aligned(32)))` / `aligned_alloc` / 链接脚本里划对齐段 |
| 长度不是整数倍 | 向上取整到扇区 / 页边界，多出的部分补齐（`0xFF` 或 `0x00`，看介质要求） |
| 上层给的是任意指针 | 加 **bounce buffer** 中转：先 memcpy 到对齐缓冲区，DMA 搬完再拷回 |
| Cache 不一致 | 传输前 `clean`（写回）、传输后 `invalidate`（作废）；或把 buffer 放 non-cacheable 区 |
| 性能差 | 用双缓冲乒乓，别每包都 memcpy |

## 五、RTOS 与操作系统

### R01 · FreeRTOS 如何查看堆内存使用情况 `[富兰瓦时]`

| API | 看什么 |
|---|---|
| `xPortGetFreeHeapSize()` | 当前剩余堆字节数 |
| `xPortGetMinimumEverFreeHeapSize()` | **历史最小**剩余（跑过最坏场景才有意义） |
| `uxTaskGetStackHighWaterMark(handle)` | 单个任务栈的**历史最小**剩余（单位是 word） |
| `vTaskList(buf)` | 所有任务的状态、优先级、栈剩余、序号 |
| `uxTaskGetSystemState()` | 结构化版本，可自己解析 |

**注意**

- `configTOTAL_HEAP_SIZE` 在 `FreeRTOSConfig.h` 里定总大小
- `heap_4` 有碎片问题：**剩余总量够，不代表能分配出一块大的** —— 要看最大连续块
- `vTaskList` 需要 `configUSE_TRACE_FACILITY` 和 `configUSE_STATS_FORMATTING_FUNCTIONS` 打开，且比较占栈

### R02 · 为什么绑核可能减少开销，上下文切换如何发生 `[A]`

**绑核（CPU affinity）为什么省开销**

1. **Cache 局部性**：任务迁移到新核，目标核的 L1/L2 是冷的，要重新加载，绑核后热数据留着
2. **TLB 不失效**：换核可能触发 TLB 刷新
3. **减少迁移开销**：调度器迁移本身要发 IPI（核间中断）、加锁
4. **避免跨核竞争**：同一份数据固定在一个核上访问，减少缓存行 bouncing

**代价**：绑死会失去负载均衡，某个核忙死另一个核闲着。

**上下文切换如何发生**

| 触发源 | 说明 |
|---|---|
| 时间片耗尽 | SysTick 中断里判断当前任务时间片用完 |
| 更高优先级就绪 | 任务被唤醒 / 信号量释放 / 中断里 `xSemaphoreGiveFromISR` |
| 任务主动让出 | `vTaskDelay`、等队列、等信号量 |
| 中断退出时 | `portYIELD_FROM_ISR` 触发 PendSV |

**切换过程**（Cortex-M 为例）

1. 触发 PendSV 异常（最低优先级，保证不打断其他中断）
2. 硬件自动压栈 R0–R3、R12、LR、PC、xPSR
3. 手动保存剩余寄存器 R4–R11 到任务栈
4. 把当前 SP 存回 TCB，更新任务状态
5. 调度器选出下一个任务，从它的 TCB 取 SP
6. 恢复 R4–R11，硬件自动出栈，返回新任务

### R03 · 进程间通信的方式 `[B]`

| 方式 | 特点 |
|---|---|
| 管道 pipe / 命名管道 FIFO | 半双工，字节流，FIFO 可用于无亲缘关系进程 |
| 消息队列 | 有消息边界，可按类型取 |
| 共享内存 | **最快**（零拷贝），但**必须配信号量同步** |
| 信号量 | 用于同步 / 互斥，不传数据 |
| 信号 signal | 异步事件通知，信息量极小 |
| Socket | 可跨主机，最通用 |
| 内存映射文件 mmap | 文件即共享内存，可持久化 |

### R04 · 两个进程之间如何共享信息 `[B]`

**标准答案：共享内存 + 信号量**

```c
shmid = shmget(key, size, IPC_CREAT | 0666);
p = shmat(shmid, NULL, 0);   // 两个进程各自 shmat，拿到同一块物理页
```

**关键点**：共享内存本身**不提供任何同步机制**，必须额外用信号量 / 互斥锁 + 条件变量保护，否则读到写一半的脏数据。

其他方案：消息队列、管道、socket、mmap 共享文件。数据量小用消息队列更简单，量大用共享内存。

### R05 · 进程和线程的 API，创建进程线程 `[B]`

**创建进程**

```c
pid_t pid = fork();          // 返回两次：父进程得子 PID，子进程得 0，失败 -1
if (pid == 0) {
    execl("/bin/ls", "ls", NULL);   // 子进程替换为新程序
    _exit(1);                        // exec 失败才走到这
}
waitpid(pid, &status, 0);    // 父进程回收，防僵尸
```

**创建线程**

```c
int pthread_create(pthread_t *tid, const pthread_attr_t *attr,
                   void *(*start_routine)(void *), void *arg);
pthread_join(tid, &ret);     // 阻塞等待回收
// 或 pthread_detach(tid) 让线程结束时资源自动回收
```

**核心区别**：进程有独立地址空间（`fork` 后写时拷贝），线程共享地址空间（只需切换栈和寄存器），所以线程切换更轻。

### R06 · FreeRTOS 优先级反转怎么产生，怎么缓解 `[泰凌微]`

**产生过程（三步，必须说清）**

1. 低优先级任务 **L** 拿到了互斥量，开始访问共享资源
2. 高优先级任务 **H** 就绪，要这把锁 → 阻塞等 L 释放
3. 中优先级任务 **M** 就绪，抢占了 L（L 优先级最低）→ L 迟迟跑不完 → **H 被 M 间接拖住**

结果：H 的响应时间取决于 M 跑多久，优先级形同虚设。

**缓解手段**

| 手段 | 做法 | 代价 |
|---|---|---|
| **优先级继承**（FreeRTOS 互斥量默认支持） | L 持锁期间临时提升到 H 的优先级，释放后恢复 | 实现简单，但只解决"一把锁" |
| **优先级天花板** | 任何任务拿这把锁时，直接把优先级抬到"可能用这把锁的最高优先级" | 更彻底，需要静态分析 |
| 缩短临界区 | 持锁期间不做耗时 IO、不 delay | 最根本，但要求代码纪律 |
| 避免共享 | 用消息队列替代共享内存 | 增加拷贝开销 |

**容易错的点**：**二值信号量没有优先级继承，互斥量才有。** 用二值信号量做资源保护 = 主动埋了反转的雷。这是 FreeRTOS 面试的高频坑。

### R07 · 队列、信号量、互斥量、事件组的区别与适用场景 `[泰凌微]`

| 机制 | 传数据？ | 关键特性 | 典型场景 |
|---|---|---|---|
| **队列 Queue** | ✔ 拷贝数据 | 有深度、可阻塞、FIFO | 任务间传数据包、传感器读数 |
| **二值信号量** | ✘ | 只有 0/1，**无优先级继承** | 任务同步、中断通知任务"有事件了" |
| **计数信号量** | ✘ | 计数上限 | 资源池计数（如 5 个缓冲区） |
| **互斥量 Mutex** | ✘ | **有优先级继承**、可递归版本 | 保护共享资源、共享总线 |
| **事件组 EventGroup** | ✘（位标志） | 多事件组合等待、一对多 | "DMA 完成 **且** 超时未发生"才继续 |
| **任务通知** | ✔（一个 32 位值） | 最轻量、最快，**一对一** | 替代二值信号量/简单队列 |

**选择原则（背这句）**

> 传命令用队列，传大数据用共享缓冲 + 互斥，保护临界区用互斥量，中断通知任务用二值信号量，多条件组合等待用事件组。

**为什么互斥量比二值信号量"贵"**：它要维护持有者、支持优先级继承、支持递归，代码路径长一些，但换来的是不会踩反转。

### R08 · 中断里能不能直接调用带阻塞的 RTOS API `[泰凌微]`

**不能。**

**原因**

1. 中断上下文**没有任务 TCB**，阻塞意味着"让出 CPU 等条件"，但中断不是任务，无处可让
2. 中断上下文里调度器状态不一致，强行切任务会破坏内核假设
3. 阻塞时间不可控，直接拉长中断延迟，影响实时性

**正确做法**

- 一律用 **FromISR 版本**：`xQueueSendFromISR`、`xSemaphoreGiveFromISR`、`xEventGroupSetBitsFromISR`
- 如果该 API 可能引起任务切换，需要 `portYIELD_FROM_ISR(xHigherPriorityTaskWoken)`
- ISR 里只做**三件事**：置标志、发队列/信号量、清中断标志。复杂处理扔给任务

**常见 Bug 现场**

在 ISR 里误调了普通版 `xQueueSend` → 偶发 HardFault 或调度错乱，且**只在特定时序下复现**，极难查。

> 追问："那 ISR 里能调用 `vTaskDelay` 吗？" → 不能，`vTaskDelay` 就是阻塞。同理 `printf` 在 ISR 里也危险（可能内部加锁/耗时），要用精简版日志或环形缓冲。

### R09 · RTOS 任务切换时，上下文需要保存哪些东西 `[泰凌微]`

**必须保存**

- 通用寄存器 `R0–R12`
- 栈指针 `SP`（存回 TCB）
- 链接寄存器 `LR`（返回地址）
- 程序计数器 `PC`
- 状态寄存器 `xPSR` / `CPSR`

**Cortex-M 的分工（能说出这个细节就是加分）**

| 谁保存 | 保存什么 |
|---|---|
| **硬件自动压栈** | `R0–R3`、`R12`、`LR`、`PC`、`xPSR`（8 个字） |
| **软件（PendSV）补压** | `R4–R11`（8 个字） |

**开了 FPU 且任务用了浮点**

还要保存 `S0–S15` + `FPSCR`。Cortex-M4F 支持 **lazy stacking**（先不压，真用了浮点才补压），但如果 ISR 里也用了浮点，必须手动把 `FPCCR.ASPEN/LSPEN` 配好，否则会踩坏任务浮点上下文。

**不保存**：全局变量、堆内容、外设寄存器（这些不属于"上下文"，除非任务自己保存）

**存到哪**：全部压进**该任务自己的栈**，`TCB` 里只存一个 `SP` 指针。切换 = 换 SP。

## 六、低功耗与系统可靠性

### L01 · MCU 休眠功耗如何判断是否合理，异常时如何排查 `[A][泰凌微]`

**先判断"合理"**

1. 查 datasheet 里该休眠模式的**典型值 / 最大值**，建立基准（比如 STOP2 模式 2μA）
2. 用高精度源表（Keysight N6705 之类）或万用表 μA 档测，**测的时候要断开调试器、拔掉所有外设**
3. 实际值超过典型值 2–3 倍就是异常，超过一个数量级肯定是漏电

**异常排查（从外到内）**

1. **GPIO**：悬空引脚必须配成推挽输出低 / 上拉输入，浮空输入会因电平不确定导致输入级来回翻转耗电
2. **外设时钟**：所有没用到的外设时钟关掉（`RCC->APB1ENR` 逐个清）
3. **模拟模块**：ADC、比较器、LDO 内部基准，休眠时是否还在工作
4. **外部电路**：上拉电阻在休眠时的漏电、分压电阻的常态电流、LED 限流电阻
5. **看门狗 / RTC**：低频时钟是否还在跑，能不能关
6. **调试口**：SWD/JTAG 引脚在低功耗模式下可能持续漏电，要么关掉，要么配成模拟
7. **分段断电**：逐个模块断电测电流，差值就是它的功耗

> 详见：泰凌微 Q17

### L02 · 只有 TX/RX 的 MCU 与休眠模组如何完成唤醒和接收 `[A]`

场景：MCU 进低功耗，外部通信模组（蓝牙 / 4G / LoRa）收到数据后要把 MCU 叫醒。

**方案一：模组有中断脚（最优）**

模组通常有 `RI` / `INT` / `WAKEUP` / `READY` 之类引脚，接 MCU 的 EXTI 外部中断：

1. 进休眠前把该脚配成**上拉输入 + 下降沿触发中断**
2. 模组收到数据拉低该脚 → MCU 被唤醒
3. MCU 醒来等时钟稳定（等 HSI/PLL ready），再初始化 UART 把模组 FIFO 里的数据读走

**方案二：真的只有 TX/RX 两根线**

利用 **UART 的起始位唤醒功能**（很多 MCU 的 LPUART 支持）：

1. 休眠前把 RX 脚配成**上拉输入 + 下降沿中断**（不能浮空，否则误唤醒）
2. 模组发数据时，起始位的下降沿触发唤醒
3. 唤醒后立刻切回 UART 功能，接收这一帧 —— **注意这帧开头的几个 bit 可能已经丢了**，所以要么让模组重发，要么只把这次唤醒当"有数据了"的通知，醒来后再正式请求数据

**方案三：让模组负责缓存**

模组先把数据收进自己的 FIFO，等 MCU 定时醒来（或靠一根 GPIO 通知）再一次性读走。牺牲实时性换功耗。

**关键细节**

- RX 引脚休眠时必须固定电平，浮空会因噪声频繁误唤醒，反而更费电
- 唤醒后要等时钟稳定再开 UART，否则前几个字节必错
- 唤醒源要能在休眠模式里生效（有些 MCU 的深度休眠只认特定几个引脚）

### L03 · 单片机莫名重启可能有哪些原因，如何排查 `[富兰瓦时]`

**原因分类**

| 大类 | 具体 |
|---|---|
| 电源 | 电压跌落 / 尖峰、LDO 带载能力不足、电池内阻大、大电流瞬间（射频发射、电机启动）拉垮电源 |
| 复位电路 | NRST 被干扰耦合、复位电容失效、外部复位芯片误动作 |
| 看门狗 | 喂狗超时（任务阻塞、中断风暴、死循环、优先级反转） |
| 软件 | HardFault：空指针、野指针、数组越界改坏返回地址、栈溢出、除零、非对齐访问 |
| 时钟 | 晶振停振、PLL 失锁、时钟切换失败（切到还没稳定的时钟源） |
| 环境 | ESD、浪涌、继电器 / 电机反电动势、高温 |

**排查顺序（第一步就能砍掉一半可能）**

1. **读复位原因寄存器** —— STM32 的 `RCC->CSR` 里有 `PORRSTF`（上电）、`PINRSTF`（复位脚）、`IWDGRSTF`（独立看门狗）、`WWDGRSTF`（窗口看门狗）、`SFTRSTF`（软件复位）、`BORRSTF`（欠压）、`LPWRRSTF`（低功耗）
   - 是 IWDG → 查喂狗逻辑
   - 是 PIN → 查硬件干扰
   - 是 POR/BOR → 查电源
   - 是 SFT → 查 `NVIC_SystemReset` 被谁调了
2. **保存现场**：把复位瞬间的 PC、LR、关键变量写进 noinit RAM（复位不清零的段）或 Flash，重启后回读
3. **HardFault 回溯**：从异常栈里取出压栈的 PC，用 `addr2line` 定位到源码行
4. **示波器盯 VDD 和 NRST**，抓复位瞬间波形，看有没有跌落
5. **对照实验**：临时关掉看门狗 / 加大超时，看是否还重启，判断是不是喂狗问题

### L04 · 芯片上电无法运行怎么排查 `[泰凌微]`

按"电 → 复位 → 时钟 → 启动 → 程序"逐级往上：

1. **电源**：各路电压是否正常、有无压降、纹波多大
2. **复位**：NRST 电平是否被一直拉低
3. **时钟**：外部晶振是否起振（示波器探头接晶振脚，注意探头电容会影响起振）
4. **BOOT 引脚**：启动模式配置对不对（从 Flash 还是从 System Memory 启动）
5. **程序是否下载成功**：读回 Flash 校验
6. **硬件短路**：电源对地阻抗
7. **调试器能否连上**：连不上说明芯片没跑起来或时钟有问题；能连上就单步跟到 `main`

> 详见：泰凌微 Q21

### L05 · 电源架构：DCDC 和 LDO 怎么选 `[补充]`

**本质区别**

| | LDO（线性稳压） | DCDC（Buck 开关稳压） |
|---|---|---|
| 原理 | 调整管当可变电阻，多余电压变热耗掉 | 开关管 + 电感储能，能量搬移 |
| 效率 | `≈ Vout / Vin`（压差越大越低） | 85%–95%，压差大也不明显下降 |
| 发热 | 压差大时严重 | 小 |
| 噪声 / EMI | **低**（无开关动作） | 有开关纹波和 EMI，需布局讲究 |
| 外围器件 | 只需输入输出电容 | 需要**电感**、电容，占板面积大 |
| 静态电流 Iq | 可做到 μA 级甚至 nA 级 | 通常 μA 级，轻载效率是难点 |

**选型口径**

- **电池供电 + 压差大**（如 4.2V 锂电降到 1.8V）→ 必须 DCDC，LDO 会把 57% 的能量烧成热
- **射频 / ADC / RTC 供电** → LDO 或 DCDC 后级再挂 LDO，压纹波
- **超低功耗待机** → 看 `Iq` 而不是看满载效率，轻载效率才是关键
- **成本敏感、板子小** → LDO

**低功耗产品的常见做法**

> 正常工作时走 DCDC（效率高、省电），休眠时切到超低 Iq 的 LDO（DCDC 的静态损耗和轻载效率此时反而更差）。这颗开关可以用 GPIO 控制。

**面试延伸**：为什么 BLE 产品对电源这么敏感？
→ 射频发射瞬间电流可到 10–20mA，如果电源响应慢（LDO 环路慢、电池内阻大），会瞬间掉压导致射频异常或复位。所以要在射频电源脚就近放 10–100μF 电容做电荷缓冲。

## 七、无线与 USB

### W01 · 了解无线协议吗 `[A][泰凌微]`

**答题策略**：先深说一个最熟的（BLE），再用一句话横向对比其他，最后坦白边界。

**BLE（重点展开）**

- 低功耗蓝牙，面向短包、低占空比
- **GAP** 管广播 / 扫描 / 连接；**GATT** 管数据结构（Service → Characteristic → Descriptor）
- 广播包（BLE 4.x 最大 31 字节，BLE 5 扩展广播可到 255）
- 连接事件 + 连接间隔（最小 7.5ms，越小越实时越费电）
- 应用：遥控器、传感器、灯控、穿戴

**横向对比（一句话一个）**

| 协议 | 底层 | 拓扑 | 特点 |
|---|---|---|---|
| BLE | 自有 | 星型 / 点对点 | 低功耗、短包、手机直连 |
| Zigbee | IEEE 802.15.4 | **Mesh** | 节点多、自组网、智能家居 |
| Thread | 802.15.4 + IPv6 | Mesh | 原生 IP，Matter 的底座 |
| Wi-Fi | 802.11 | 星型 | 高速、高功耗、直连路由 |

**收尾话术**：`"BLE 我做过完整的 GAP/GATT 流程；Zigbee 和 Thread 都是 802.15.4 上的 Mesh 方案，我了解分层架构和组网思路，但没做过实际项目。"` —— 比硬吹更可信。

> 详见：泰凌微 Q18

### W02 · 熟悉 USB 协议吗，USB 有几种传输方式 `[A]`

**4 种传输类型**

| 类型 | 保证什么 | 典型用途 | 特点 |
|---|---|---|---|
| **控制 Control** | 送达 + 顺序 | 枚举、配置、命令 | 双向，端点 0 必备，每个设备都有 |
| **中断 Interrupt** | **最大延迟** | HID 键盘 / 鼠标 | 小数据量，主机定时轮询（不是真的中断） |
| **批量 Bulk** | **数据正确**，不保证带宽 | U 盘、打印机 | 大数据量，总线空闲时占满带宽，有重传 |
| **等时 Isochronous** | **带宽 / 时序**，不保证正确 | 音频、视频 | 固定时间片，**无重传**，允许丢包 |

**记忆法**：控制=枚举、中断=小而定时、批量=大而准确、等时=实时可丢。

**补充**：USB 2.0 高速 480Mbps、全速 12Mbps、低速 1.5Mbps；主机主导，所有传输由主机发起，设备不能主动发数据。

### W03 · 常见 USB 描述符有哪些 `[A]`

描述符是一棵**树**，枚举时主机逐级读取：

```
设备描述符 Device
└── 配置描述符 Configuration
    └── 接口描述符 Interface
        └── 端点描述符 Endpoint
```

| 描述符 | 关键字段 |
|---|---|
| **设备 Device** | VID / PID、bcdUSB、设备类、端点 0 最大包长、配置数量 |
| **配置 Configuration** | 供电方式（自供电 / 总线供电）、最大电流、接口数量 |
| **接口 Interface** | 接口类 / 子类 / 协议（如 HID=3）、端点数 |
| **端点 Endpoint** | 端点号 + 方向、传输类型、最大包长、轮询间隔 |
| **字符串 String** | 厂商、产品、序列号（UTF-16LE 编码） |

**其他**：HID 描述符 + 报告描述符（Report Descriptor，描述数据格式）、BOS 描述符、设备限定描述符、OTG 描述符。

### W04 · BLE 协议栈分几层，各层干什么 `[泰凌微]`

这是进泰凌微**最该背熟的一张图**。

```
┌─ App ──────────────────── Profile（HID / 电量 / 心率…）
├─ Host ────── GAP   通用访问：角色、广播、连接参数、配对
│              GATT  通用属性：Service / Characteristic 的组织
│              ATT   属性协议：读/写/通知 的具体操作与句柄
│              SM    安全管理：配对、绑定、密钥
│              L2CAP 逻辑链路：多路复用（ATT 通道 / SMP 通道）、分包重组
├─ Controller ─ LL   链路层：广播、扫描、连接、跳频、重传
└────────────── PHY  物理层：2.4GHz、40 信道、1M/2M PHY
```

**三层职责一句话**

- **Controller**：管"空口怎么发" —— 调制解调、跳频、时序
- **Host**：管"发什么、发给谁、安不安全"
- **App**：管"这些数据是什么意思"

**必须分清的两个**

| | GAP | GATT |
|---|---|---|
| 管什么 | **怎么被发现、怎么连上** | **连上之后有什么数据、怎么读** |
| 关键词 | 角色、广播、扫描、连接参数、配对 | Service、Characteristic、UUID、句柄、Notify |
| 一个比喻 | 门牌号和敲门方式 | 屋里的文件柜怎么分类 |

> **高频错误**：把 GAP 和 GATT 说混。面试官听到"GATT 负责广播"基本就不想往下问了。

**四种 GAP 角色**：Broadcaster（只广播）、Observer（只扫描）、Peripheral（广播并接受连接，从机）、Central（扫描并发起连接，主机）。

**SMP / 加密**：配对后链路用 AES-128-CCM 加密。BLE 4.2 起有 LE Secure Connections（ECDH），比老版配对强。注意"Just Works"配对只加密不防中间人。

### W05 · 广播模式和连接模式有什么区别 `[泰凌微]`

| | 广播（Advertising） | 连接（Connected） |
|---|---|---|
| 拓扑 | 一对多，无连接 | 点对点 |
| 信道 | 3 个广播信道 **37 / 38 / 39** | 37 个数据信道 0–36，**自适应跳频** |
| 可靠性 | **无 ACK、无重传** | 有 ACK、有重传 |
| 载荷 | 31 字节（BLE 5 扩展广播可到 255） | 受 MTU 限制（默认 23，可协商到 247+） |
| 时序 | 广播间隔 20ms – 10.24s | 连接间隔 7.5ms – 4s + 从机延迟 |
| 双向 | 单向 | 双向 |
| 加密 | 无 | 可加密 |

**典型设计模式**：先用广播被发现并携带设备标识，连上后再走 GATT 做配置和传输。低功耗传感器甚至可以**只广播不连接**（ibeacon、温湿度广播），彻底省掉连接维护开销。

**广播包内容**：长度 + AD Type + AD Data，常见类型有 Flags、Local Name、Service UUID、Manufacturer Specific Data（厂商自定义，最常用）。

### W06 · BLE OTA 升级怎么实现（附：牵不牵扯波特率）`[泰凌微]`

**标准流程**

1. **分包**：固件切成 N 包，每包带序号
2. **传输**：通过自定义 GATT Characteristic 下发（主机 `Write` 或从机 `Notify` 拉取）
3. **写 Flash**：落到 OTA 分区（双 bank 时写非运行区）
4. **校验**：每包 CRC + 整包 CRC / 签名
5. **置标志**：全部完成后写"升级请求"标志
6. **重启进 Bootloader**：Bootloader 校验新固件 → 搬运或切换 bank → 跳转

**三个必须提的工程点**

- **断电保护**：记录已接收偏移 + 分块 CRC，断电后能续传，不用从头再来
- **回滚**：双 bank 保证新固件校验失败还能回旧版
- **传输速率**：受 MTU、连接间隔、每包重传次数影响，实际吞吐通常几十 KB/s

> **陷阱题**：面经里问"OTA 牵扯到波特率吗？"
> **答案：BLE OTA 不涉及波特率**。波特率是 UART / CAN 这类异步串行总线的概念；BLE 决定吞吐的是 **MTU 大小、连接间隔、PHY 速率（1M/2M）、每连接事件能发几包**。
> 但如果你的 OTA 是"MCU 通过 UART 把固件转发给蓝牙模组"，那才牵扯波特率。**先问清架构再答**，这一句本身就是加分项。

### W07 · 如何降低 BLE 功耗 `[泰凌微]`

按"射频 → 协议参数 → 系统"三层答：

**射频层**

1. 降低发射功率 `TX Power`（按距离动态调，省得最多）
2. 用 **2M PHY** 缩短每次收发的时间
3. 关闭不用的功能（如可扫描、扩展广播）

**协议参数层（核心）**

4. **加大广播间隔**：100ms → 1s，平均功耗差约 10 倍
5. **加大连接间隔** `Connection Interval`：与主机协商更大值
6. **启用从机延迟** `Slave Latency`：没有数据时跳过 N 个连接事件
7. **用 Notify 代替 Read**：Notify 是服务端主动推，Read 要主机轮询

**系统层**

8. MCU 在连接事件之间进**深度睡眠**，靠定时器精确唤醒（要求唤醒快、时钟准）
9. 减少广播载荷和 GATT 交互次数
10. 缩短射频开启时间窗（校准好时序，别提前太久开）

**算一笔账（面试可以说）**

> 广播间隔 1s、每次广播事件射频开 3ms、峰值 10mA，平均电流 ≈ `10mA × 3ms / 1000ms = 30μA`。用 230mAh 的纽扣电池，理论续航 ≈ 7000 小时。

### W08 · 经典蓝牙和 BLE 的区别 `[补充]`

| | 经典蓝牙（BR/EDR） | BLE |
|---|---|---|
| 定位 | 持续连接、大数据流 | 短包、低占空比 |
| 典型用途 | 音频（A2DP）、文件传输、串口 SPP | 传感器、遥控、穿戴、ibeacon |
| 功耗 | 高（mA 级） | 极低（μA 级平均） |
| 连接建立 | 慢（秒级） | 快（ms 级） |
| 拓扑 | 点对点 / piconet | 广播一对多 + 连接点对点 |
| 吞吐 | 高（2–3Mbps） | 低（几十 KB/s ~ 1.4Mbps） |
| 信道 | 79 个 1MHz | 40 个 2MHz |

**一句话**：要传音频和文件用经典；要电池撑几个月、只发几个字节用 BLE。市面上多是**双模芯片**，两套协议都支持。

## 八、C++ 相关

### X01 · new 和 malloc 的区别 `[B]`

| | `new` | `malloc` |
|---|---|---|
| 本质 | **运算符**（可重载） | **库函数** |
| 构造 / 析构 | 调用构造函数 / `delete` 调析构 | 只管内存，不调构造 |
| 返回类型 | **类型化指针** | `void*`，C++ 里需强转 |
| 大小计算 | 编译器自动算 | 手动 `sizeof` |
| 失败行为 | 抛 `std::bad_alloc`（`nothrow` 版返回 NULL） | 返回 NULL |
| 内存来源 | 最终也走 `operator new` → 通常还是 malloc | 堆 |

**铁律：不能混用** —— `new` 出来的必须 `delete`，`malloc` 出来的必须 `free`，混用是未定义行为。`new[]` 必须配 `delete[]`，否则只调第一个元素的析构。

### X02 · 什么是多态，多态的作用 `[B]`

**定义**：同一接口，不同实现 —— 用基类指针 / 引用调用同一个虚函数，实际执行的是对象**真实类型**的版本。

**两类**

- **编译期多态**（静态）：函数重载、模板 —— 编译时就确定调哪个
- **运行期多态**（动态）：虚函数 + 基类指针 —— 运行时查虚表

**实现机制**

每个含虚函数的类有一张**虚函数表 vtable**，对象头部有一个**虚表指针 vptr** 指向它。调用 `p->func()` 时，通过 `vptr` 找到 vtable，再按偏移取出函数地址 —— 这是"一次间接跳转"的开销，比普通调用慢，也阻碍内联。

**作用**

1. **解耦**：上层只依赖抽象接口，新增子类不用改上层代码（开闭原则）
2. **可扩展**：插件架构、状态机、驱动抽象层
3. **嵌入式场景**：不同传感器统一 `read/write` 接口；不同通信方式统一 `send/recv`

### X03 · 什么函数不能定义为虚函数，构造函数为什么不能是虚函数 `[B]`

**不能是虚函数的**

1. **构造函数** —— vptr 还没初始化，见下
2. **静态成员函数** —— 不属于任何对象，没有 `this`，无法通过 vptr 调用
3. **内联函数** —— 编译期展开与运行期动态绑定矛盾（声明 virtual 后编译器会忽略 inline）
4. **友元函数** —— 它不是类的成员
5. **普通全局函数** —— 同上

**构造函数为什么不能是虚函数（三层理由，建议全说）**

1. **机制上不可能**：虚函数调用依赖 vptr，而 vptr 正是在**构造函数里**才被初始化的 —— 鸡生蛋问题
2. **语义上不成立**：虚函数的意义是"通过基类指针调用派生类实现"，但创建对象时编译器**必须知道确切类型**才能算出要分配多少内存，虚函数给不出确定大小
3. **语法上不允许**：构造函数没有返回值、不能取地址，vtable 里根本没有它的位置

**必须补的一句**：**析构函数应该声明为虚函数**。否则用基类指针 `delete` 派生类对象时，派生类的析构不会被调用 → 资源泄漏。这是面试官最爱追的反向问题。

## 十、中断与异常处理

### I01 · 如何理解中断，中断处理流程是什么 `[泰凌微]`

**定义**：CPU 在执行主程序时，被外部或内部事件打断，转去执行对应的处理函数，完成后回到断点继续。

**价值**：替代轮询，让 CPU 不必空转等事件 —— 这是低功耗设计的基础（不做事就睡觉，有事再醒）。

**处理流程**

1. 中断源发出请求，置位中断标志
2. NVIC 判断优先级，决定是否响应
3. **保护现场**：压栈 `PC`、`xPSR`、`LR`、`R0-R3`、`R12`（Cortex-M 硬件自动完成）
4. 从**中断向量表**取出 ISR 入口地址，跳转
5. 执行 ISR（清中断标志！）
6. **恢复现场**：出栈，返回断点

**Cortex-M 的几个关键细节**

- 向量表默认在 `0x00000000`，可以通过 `SCB->VTOR` 重定位（Bootloader 跳 APP 时必须改）
- 进入异常时 `LR` 被写入特殊的 `EXC_RETURN` 值，告诉我们"从哪来、用哪个栈"
- 尾链（tail-chaining）：连续两个中断之间不做出栈再入栈，省时间

### I02 · 中断优先级与嵌套怎么配置 `[泰凌微]`

**Cortex-M 的优先级模型**

- 每个中断有一个 8 位优先级寄存器，实际实现位数由芯片决定（常见 4 位 = 16 级）
- **数值越小，优先级越高**（这是最容易答反的点）
- 优先级分两段：**抢占优先级**（能不能打断正在执行的 ISR）+ **子优先级**（同时挂起时谁先执行）

| 情况 | 结果 |
|---|---|
| 抢占优先级不同 | 高的可以**打断**低的（中断嵌套） |
| 抢占相同、子优先级不同 | **不能互相打断**，但同时挂起时子优先级高的先执行 |
| 两者都相同 | 按中断号排，号小的先 |

**优先级分组** `NVIC_PriorityGroup`：决定几位给抢占、几位给子优先级。分组一旦定下，全工程统一，中途改会导致已有配置错乱。

**工程实践**

- 别把所有中断都设成最高优先级，否则失去嵌套意义
- 对实时性要求高的（如 BLE 连接事件、电机换相）给高抢占
- 低速外设（UART 收字节、按键）给低抢占
- **临界区里关中断会拉长所有中断的响应时间**，要尽量短

### I03 · HardFault 怎么排查 `[泰凌微]`

**第一步：看故障状态寄存器（这一步定生死）**

| 寄存器 | 看什么 |
|---|---|
| `SCB->CFSR` | 细分故障原因，分三部分：`UFSR`（用法错误）、`BFSR`（总线错误）、`MMFSR`（内存管理错误） |
| `SCB->HFSR` | 是否是硬 fault 升级而来（`FORCED` 位） |
| `SCB->BFAR` | 触发总线错误的具体地址（需 `BFHFNMIGN` 配合） |
| `SCB->MMFAR` | 触发内存管理错误的地址 |

**CFSR 里最常见的几位**

- `UFSR.UNDEFINSTR`：执行到非法指令 → 跑飞到数据区
- `UFSR.INVSTATE`：试图进入 ARM 状态（函数指针低 bit 被置 0）
- `UFSR.UNALIGNED`：非对齐访问
- `BFSR.PRECISERR`：精确总线错误 → 地址有效但访问非法（`BFAR` 里有地址）
- `BFSR.IMPRECISERR`：不精确 → 写缓冲导致，现场已丢，只能靠日志

**第二步：从栈里取现场**

```c
// 判断用的是 MSP 还是 PSP（看 EXC_RETURN 的 bit2）
// 从对应栈里按顺序取出 R0,R1,R2,R3,R12,LR,PC,xPSR
// PC 就是出错那条指令的地址
```

**第三步：定位源码**

拿 `PC` 值 → 用 `arm-none-eabi-addr2line -e xxx.elf 0x08001234` → 得到 `文件:行号`。

**常见根因清单**

空指针解引用、野指针、数组越界改坏返回地址、栈溢出、函数指针未初始化/被踩、非对齐访问、访问了未使能时钟的外设（总线错误）。

**工具**：Keil / IAR 自带 Fault 分析窗口；J-Link + GDB；开源库 **CmBacktrace**（自动解析并打印调用栈，强烈推荐）。

### I04 · 如何判断是栈溢出还是堆被踩 `[泰凌微]`

**症状对比**

| | 栈溢出 | 堆被踩 |
|---|---|---|
| 典型现象 | 局部变量莫名被改、函数返回后跑飞、HardFault 时 SP 超出栈范围 | `malloc` 后数据错乱、`free` 时崩（arena 损坏）、相邻块头部被改 |
| 崩溃位置 | 常发生在**函数返回**那一刻 | 常发生在**下一次 malloc/free** |
| 触发条件 | 深调用链、大局部数组、递归、中断嵌套 | 写越界、用了已 free 的指针、长度算错 |

**检测手段**

**栈**

```c
// 1. 栈底填魔数，周期性检查是否被改写
#define STACK_MAGIC 0xDEADBEEF
// 2. FreeRTOS 开启栈溢出钩子
void vApplicationStackOverflowHook(TaskHandle_t xTask, char *pcTaskName);
// 3. 看栈水位
uxTaskGetStackHighWaterMark(NULL);
// 4. 硬件：MPU 保护栈边界，越界立即 fault
```

**堆**

- 分配时在块头/块尾加 canary，free 前校验
- 包装 `malloc/free`，记录每次分配的大小和调用点
- Linux 下用 ASan；嵌入式可用 `FreeRTOS` 的 `heap_4` + 完整性检查 `configUSE_MALLOC_FAILED_HOOK`

**一句话判断法**：崩溃点紧跟某个函数调用/返回 → 偏栈；崩溃点紧跟一次分配/释放 → 偏堆。

### I05 · 程序跑飞 / 死机，通用定位方法 `[泰凌微]`

**核心原则：先保住现场，再谈复现。**

1. **保留现场**
   - HardFault handler 里把 `CFSR/HFSR/BFAR/PC/LR/SP` 写进 **noinit RAM**（复位不清零）或 Flash
   - 重启后第一件事：读出来打印
2. **确定是不是真复位**
   - 读复位原因寄存器（见 L03），区分"自己复位"和"看门狗拉回"
3. **缩小范围**
   - 二分法：屏蔽模块 / 注释功能，看是否还挂
   - 分级日志 + 状态机打点，看最后走到哪一步
4. **构造复现**
   - 加压力（高频中断、满负载、连续收发）
   - 改时序（加/减延时，看是否与竞态相关）
   - 拉开条件（温度、电压、长时间老化）
5. **看时序**
   - 逻辑分析仪抓总线，示波器抓电源和复位脚
   - J-Link RTT / SWO 做非侵入式日志

**经验规律**

- **越难复现的 bug，越可能是并发/时序问题**（中断与主循环共享变量没保护、临界区不够）
- **只在长时间运行后出现**，优先怀疑内存泄漏和计数器溢出
- **只在特定板子上出现**，优先怀疑硬件（虚焊、电源、晶振）

## 十一、启动流程、固件与存储

### B01 · 从上电到 main 经历了什么 `[泰凌微]`

**六个阶段**

1. **硬件复位**：NRST 拉低再释放，CPU 从固定地址取初始 `MSP` 和 `Reset_Handler` 入口（这两个值存在向量表最前面）
2. **启动文件（startup.s）**：设置初始 SP → 调 `SystemInit()` 配置时钟（PLL、Flash 等待周期）
3. **拷贝 .data**：把 .data 段的初值从 Flash 搬到 RAM
4. **清零 .bss**：`memset(bss_start, 0, bss_size)`
5. **`__libc_init_array`**：跑 C++ 全局对象的构造函数、注册 `atexit`
6. **进入 `main()`**：初始化外设 → 创建任务 → `vTaskStartScheduler()`

**面试延伸**

- "为什么必须先配时钟再初始化外设？" → 外设挂在总线上，总线时钟没开，写寄存器会触发总线错误
- "Bootloader 跳 APP 时要注意什么？" → 见 B03：设 MSP、重定位 VTOR、关中断、跳 Reset_Handler

### B02 · Bootloader 的机制，怎么实现跳转 `[泰凌微]`

**Bootloader 是什么**：上电后**第一段运行**的程序，负责判断要不要升级、校验固件、然后跳到 APP。

**典型分区**

```
┌────────────┬──────────────┬──────────────┬──────────┐
│ Bootloader │   APP (A)    │  APP (B)     │ 参数区    │
│  固定不升级 │   运行中      │  OTA 备份     │ 升级标志  │
└────────────┴──────────────┴──────────────┴──────────┘
```

**流程**

1. 上电 → Bootloader 初始化最小外设（时钟、串口/射频、Flash）
2. 读参数区：有没有"升级请求"标志
3. **没有** → 校验 APP 区 CRC → 通过则跳转
4. **有** → 校验新固件 → 通过则擦写 APP 区或切换 bank → 清标志 → 跳转
5. 校验失败 → 保留旧固件，记录错误码

**跳转代码（Cortex-M，必背）**

```c
typedef void (*app_entry_t)(void);

void jump_to_app(uint32_t app_addr) {
    uint32_t sp = *(volatile uint32_t*)app_addr;          // 取 APP 的初始栈顶
    uint32_t pc = *(volatile uint32_t*)(app_addr + 4);    // 取 Reset_Handler

    if ((sp & 0x2FFE0000) != 0x20000000) return;          // 栈顶合法性检查（必须在 RAM 区）

    __disable_irq();                                       // 1. 关中断
    SCB->VTOR = app_addr;                                  // 2. 重定位向量表
    __set_MSP(sp);                                         // 3. 设主栈指针
    ((app_entry_t)pc)();                                   // 4. 跳过去
}
```

**四个必须做对的动作**：关中断 → 重定位 VTOR → 设 MSP → 跳 Reset_Handler。少一个就是经典 HardFault。

### B03 · 为什么用 EEPROM 而不是 Flash `[泰凌微]`

| | Flash | EEPROM |
|---|---|---|
| 擦除单位 | **按扇区/页**（1KB–4KB），不能单字节改 | **单字节**可擦写 |
| 写前要求 | **必须先擦除**（擦成 0xFF） | 可直接覆盖写 |
| 擦写寿命 | 约 1 万次 | 约 100 万次 |
| 速度 | 快 | 慢 |
| 容量 / 成本 | 大、便宜 | 小、贵 |

**结论**

- **频繁更新的少量参数**（校准值、用户设置、计数值）→ EEPROM，否则每次改一个字节都要擦 4KB，寿命很快耗尽
- **固件、大块数据** → Flash
- **折中方案**：Flash 上做**日志式存储 + 磨损均衡**，把写操作轮转到不同扇区，等价于延长寿命；或者用 FRAM（读写几乎无寿命限制）

**面试加分**：说一句"我们项目里参数存 Flash 的最后一个扇区，用了双备份 + CRC，写之前先擦，写坏了还能回退到备份"。

### B04 · RTC 芯片是什么接口，时间读出来是什么格式 `[泰凌微]`

**接口**

- 主流是 **I2C**：DS3231、PCF8563、RX8025
- 三线 SPI：DS1302
- 也有 MCU 内置 RTC（外接 32.768kHz 晶振）

**格式：BCD 码，必须自己转十进制**

```c
uint8_t bcd2dec(uint8_t bcd) { return (bcd >> 4) * 10 + (bcd & 0x0F); }
uint8_t dec2bcd(uint8_t dec) { return ((dec / 10) << 4) | (dec % 10); }
// 0x23 → 23，0x59 → 59
```

**应用场景（面经问"什么场景需要时间"）**

- 日志时间戳、定时任务（每天几点开灯）
- 低功耗产品的**定时唤醒源**（RTC 闹钟把 MCU 从 STOP 模式叫醒）
- 断电后保持时间（靠纽扣电池 / 超级电容给 RTC 域供电）

**工程注意**

- 读多个时间寄存器要**连续读（burst）**，否则跨秒时会读到"59 分 59 秒 + 下一秒的分"这种撕裂数据
- 初始化和读之前先确认 I2C 地址（DS3231 是 0x68）
- 晶振要选 32.768kHz 且负载电容匹配，否则走时不准

### B05 · DDR 时钟相关问题 `[泰凌微]`

> 这题出现在"嵌入式软件"面里，说明是芯片公司会考知识面。**不用深陷，说清概念 + 坦白边界即可。**

**基础概念**

- DDR 在**时钟的上升沿和下降沿都传数据**，所以 `数据率 = 2 × 时钟频率`（这就是 "Double Data Rate" 的含义）
- 差分时钟 `CK/CK#` 提高抗干扰
- 关键时序参数：`CL`（CAS 延迟）、`tRCD`（行激活到列选）、`tRP`（预充电）、`tRAS`

**软件侧要做什么**

1. 在 Bootloader / SPL 里配置 DDR 控制器（时序参数、刷新周期）
2. 跑 **DDR 训练**：Write Leveling（对齐写时序）、Read Gate Training（对齐读窗口）
3. 训练完做 **memtest** 验证（写图案 0xAA/0x55、地址线走 1）

**答题姿态**

> "DDR 我了解双沿传输和训练的必要性，但实际项目里 DDR 初始化代码是芯片原厂提供的，我做的是集成和验证，没独立调过时序。"

比硬编更可信。

### B06 · FreeRTOS 在 MCU 上怎么配置和移植 `[泰凌微]`

**移植要改的文件只有三个**

1. `portmacro.h` —— 数据类型和临界区宏（`portENTER_CRITICAL`）
2. `port.c` —— 栈初始化、任务切换（PendSV/SVC）、SysTick 配置
3. `FreeRTOSConfig.h` —— 功能裁剪

**配置里最该关注的**

| 宏 | 作用 | 建议 |
|---|---|---|
| `configTOTAL_HEAP_SIZE` | 堆总大小 | 按实测峰值 × 1.5 |
| `configMAX_PRIORITIES` | 优先级档数 | 别开太大，浪费 RAM |
| `configTICK_RATE_HZ` | 心跳频率 | 1000Hz（1ms）常用，太高中断开销大 |
| `configUSE_PREEMPTION` | 抢占式 | 一般开 |
| `configUSE_MUTEXES` | 启用互斥量 | 要用优先级继承就必开 |
| `configCHECK_FOR_STACK_OVERFLOW` | 栈溢出检测 | 调试期开 2，发布可关 |
| `configUSE_IDLE_HOOK` | 空闲钩子 | 进低功耗就靠它 |

**低功耗的关键接口**：空闲任务钩子 `vApplicationIdleHook()` 里判断"能不能睡"，然后执行 `WFI` 或进 STOP 模式。

> 泰凌微的 SDK 里这层基本封装好了，面试时可以说"我了解 idle hook 里进低功耗、靠中断/定时器唤醒这个模式"。

### B07 · 为什么不直接用裸机大循环，要用 RTOS `[补充]`

| | 裸机前后台 | RTOS |
|---|---|---|
| 结构 | 大循环 + 中断 | 多任务 + 调度器 |
| 实时性 | 靠中断保证关键路径，长任务会阻塞一切 | 按优先级抢占，关键任务响应有保证 |
| 可维护性 | 功能一多就变成巨型 switch | 按业务拆任务，边界清晰 |
| 资源开销 | 几乎为零 | 每个任务一份栈 + 内核 RAM，切换有开销 |
| 调试 | 简单直接 | 要理解调度、竞态、优先级 |

**判断标准**：功能少、时序简单、RAM 极紧张 → 裸机；多路并发、有通信协议栈、要保证响应时间 → RTOS。

> 面试官问这题，是想知道你会不会**用工具解决对的问题**，而不是只会 RTOS。

## 十二、工程实践与编码细节

### E01 · 如何把一个 char 变量的第 3 位置 1 `[泰凌微]`

```c
c |= (1u << 3);      // 置 1
c &= ~(1u << 3);     // 清 0
c ^= (1u << 3);      // 翻转
bit = (c >> 3) & 1u; // 读取
```

**要先确认"第 3 位"是 bit3 还是"从 1 数起的第 3 个"（= bit2）** —— 主动问一句，比答错强。

**四个常用宏**

```c
#define SET_BIT(x, n)    ((x) |=  (1u << (n)))
#define CLR_BIT(x, n)    ((x) &= ~(1u << (n)))
#define TGL_BIT(x, n)    ((x) ^=  (1u << (n)))
#define GET_BIT(x, n)    (((x) >> (n)) & 1u)
```

**注意点**

- 常量用 `1u`，避免有符号移位踩坑
- 宏的参数全部加括号（`SET_BIT(a|b, n)` 不加括号会算错）
- 多字节寄存器注意位序（大小端、MSB/LSB first）

**延伸：位域**

```c
typedef struct {
    uint32_t enable : 1;
    uint32_t mode   : 3;
    uint32_t        : 4;   // 保留
} ctrl_t;
```

位域可读性好，但**布局依赖编译器**，跨平台/协议解析时不要用，改用移位 + 掩码。

### E02 · 大端小端怎么判断（手撕代码）`[泰凌微]`

**定义**

- **大端**（Big-Endian）：高字节存低地址 —— 和人类书写顺序一致（网络字节序）
- **小端**（Little-Endian）：低字节存低地址 —— ARM/x86 常用

`0x12345678` 存到地址 `0x1000`：

| 地址 | 大端 | 小端 |
|---|---|---|
| 0x1000 | 0x12 | 0x78 |
| 0x1001 | 0x34 | 0x56 |
| 0x1002 | 0x56 | 0x34 |
| 0x1003 | 0x78 | 0x12 |

**两种写法（都要会）**

```c
// 1. 指针法
int x = 0x12345678;
char *p = (char*)&x;
printf("%s\n", (*p == 0x12) ? "大端" : "小端");

// 2. 联合体法（面试更爱看这个）
union { int i; char c; } u;
u.i = 1;
printf("%s\n", u.c == 1 ? "小端" : "大端");
```

**为什么用联合体**：所有成员共享同一块内存，`char c` 正好读到 `int` 的最低地址那个字节，不用强转指针。

**工程应用**

- **协议解析**：网络字节序是大端，本地是小端时必须转 → `htons/ntohs/htonl/ntohl`
- **Flash 存储 / 跨平台通信**：约定统一字节序
- **位域**：大小端会改变位域的填充顺序，这是跨平台 bug 的常见来源

### E03 · 环形队列怎么实现，能在任意节点插入吗 `[泰凌微]`

**基本实现**

```c
typedef struct {
    uint8_t *buf;
    uint16_t size;      // 建议取 2 的幂，取模可用 & (size-1) 加速
    volatile uint16_t head;   // 写指针
    volatile uint16_t tail;   // 读指针
} ring_t;

// 判空：head == tail
// 判满：牺牲一个单元 —— (head + 1) % size == tail
```

**为什么用「牺牲一个单元」判满**：`head == tail` 同时表示空和满，无法区分；牺牲一格就变成"满时 head 差 tail 一格"。

**单生产者单消费者的无锁写法**：`head` 只由生产者改、`tail` 只由消费者改，配合 `volatile` 和内存屏障即可无需加锁 —— 这是串口 DMA 收发的标准做法。

**"在任意节点插入"能不能做**

- **纯环形队列不支持随机插入** —— 它的语义是 FIFO，插入要么在头要么在尾。硬要在中间插，需要把后半段整体后移，O(n)，还破坏了"环形"的意义
- 如果业务真需要"按优先级/按时间插入"，数据结构应该换成**链表**或**优先队列**
- 面试这样答：**先指出语义冲突，再给替代方案** —— 比强行实现更能体现判断力

### E04 · 每个任务的 Buffer 多大，怎么判断合理性 `[泰凌微]`

这道题问的是"你有没有量化意识"。分两类答：

**任务栈大小**

1. 静态估算：最深调用链 × 每层局部变量 + 中断嵌套预留
2. 实测：跑**最坏场景**（满负荷、大量收发、深分支）后读 `uxTaskGetStackHighWaterMark()`，看历史最小剩余
3. 留 30% 以上余量，再向上取整到字对齐

**数据缓冲区大小**

1. 按**最大单包长度 × 队列深度**，加上头部/对齐开销
2. 考虑**峰值吸收能力**：例如 BLE 连接间隔 100ms 内最多来 5 包，缓冲至少要能存 5 包，否则丢包
3. 考虑**下游处理速率**：消费者最慢时会不会溢出

**怎么证明"合理"**

> 不靠拍脑袋，靠三件事：峰值场景实测 + 水位监控 + 留余量。并且把水位打印做成可观测指标，产品跑一段时间回来看数据。

### E05 · 内存对齐的优势是什么 `[泰凌微]`

**三个层面**

1. **硬件限制**：有些架构（老 ARM、部分 DSP）不允许非对齐访问，直接触发异常；Cortex-M 支持非对齐访问但有性能代价
2. **性能**：总线按字（4/8 字节）访问。一个 `int` 跨两个字边界 → 要两次总线周期再拼接
3. **原子性**：对齐的 `int` 读写通常是单条指令、天然原子；非对齐可能拆成多条，被中断打断就出错

**代价**：浪费空间。`struct { char a; int b; }` 在 32 位下占 8 字节，其中 3 字节是 padding。

**工程折中**

- **协议解析必须紧凑**：用 `#pragma pack(1)` 或 `__attribute__((packed))` 取消对齐，保证和协议字节一一对应
- 但紧凑结构体**访问会变慢**，甚至在某些平台 fault → 正确做法是**用 `memcpy` 搬到对齐的局部变量再访问**，而不是直接解引用成员

```c
#pragma pack(1)
typedef struct { uint8_t type; uint32_t len; } pkt_t;   // 5 字节
#pragma pack()
```

### E06 · 函数调用栈帧与栈回溯 `[补充]`

**栈帧里有什么**

- 函数参数（超出寄存器传参的部分）
- 返回地址（`LR`，Cortex-M 在压栈时保存）
- 上一层帧指针（如果开了帧指针）
- 局部变量、编译器产生的临时值

**为什么需要回溯**

崩溃时只知道当前 PC，不知道"是谁调过来的"。回溯能还原整条调用链，直接指向出问题的业务代码。

**两种回溯原理**

| 方法 | 原理 | 要求 |
|---|---|---|
| 帧指针链 | `R11/R7` 存上一层 FP，顺着链走 | 编译时不能省帧指针（`-fno-omit-frame-pointer`） |
| 栈扫描 | 在栈里找"看起来像返回地址"的值（落在代码段范围内） | 不需要额外信息，但可能误判 |

**实践**

- 在 HardFault handler 里把 PC/LR 和栈内容 dump 出来，PC 值拿去 `addr2line`
- 用 CmBacktrace 这类库可以自动解析并打印完整调用栈
- 注意：**开了 `-O2` 后函数可能被内联**，调用栈会"少层"，调试版本建议 `-O0` 或 `-Og`

## 十三、处理器架构

### H01 · 你对 RISC-V 了解吗，和 ARM 有什么区别 `[泰凌微]`

> 面试原话就是一句"你对 RISC-V 熟悉吗"。芯片公司爱问，因为很多国产 SoC 已经在用。
> **不用装懂，说清定位差异 + 坦白边界就是满分答案。**

**RISC-V 是什么**

- **开源指令集架构**（ISA），不是某家公司的产品，无授权费
- **模块化**：基础整数指令集 `I` + 可选扩展 `M`（乘除）/`A`（原子）/`F`/`D`（浮点）/`C`（压缩）/`V`（向量）
- 典型命名如 `RV32IMAC` = 32 位 + 乘除 + 原子 + 压缩

**和 ARM 的核心区别**

| | ARM Cortex-M | RISC-V |
|---|---|---|
| 授权模式 | 商业 IP 授权，按核收费 | 开源，免费 |
| 可定制性 | 基本不可改 | **可自由裁剪/加自定义指令** |
| 生态成熟度 | **非常成熟**，工具链/RTOS/调试器齐全 | 快速成长中，工具链在补齐 |
| 中断控制器 | NVIC（统一，好用） | CLINT（核内定时器+软中断）+ PLIC（外部中断） |
| 寄存器 | R0–R15 | **32 个**通用寄存器 `x0–x31`（`x0` 恒为 0） |
| 权限级 | Thread / Handler 两模式 | **M / S / U 三级** |
| 典型芯片 | STM32、nRF52 | 沁恒 CH32V、ESP32-C3、平头哥玄铁 |

**RISC-V 的优势与代价**

- 优势：无授权费、可按场景裁剪（IoT 芯片只要小核）、允许加自定义指令做加速
- 代价：碎片化（各家扩展不同）、生态和调试工具还不如 ARM 顺手

**答题收尾（很重要）**

> "RISC-V 我了解指令集分层和中断控制器结构，但没在 RISC-V 平台上做过完整项目，主要在 Cortex-M 上开发。"

**加分点**：提一句"从 Cortex-M 迁到 RISC-V，RTOS 移植主要改的是上下文切换那部分（寄存器布局不同）和中断控制器适配"，说明你知道实际工作量在哪。

### H02 · ARM Cortex-M 有哪些寄存器和特殊寄存器 `[补充]`

**通用寄存器**

| 寄存器 | 别名 | 作用 |
|---|---|---|
| `R0–R12` | — | 通用数据 / 传参（`R0–R3` 传前四个参数） |
| `R13` | **SP** | 栈指针，有 MSP / PSP 两个 |
| `R14` | **LR** | 链接寄存器，存函数返回地址；进异常时存 `EXC_RETURN` |
| `R15` | **PC** | 程序计数器 |

**特殊寄存器（面试常问"怎么关中断"）**

| 寄存器 | 作用 |
|---|---|
| `xPSR` | 程序状态（标志位 + 当前中断号 + 执行状态） |
| `PRIMASK` | 置 1 = **关掉所有可屏蔽中断**（只剩 NMI 和 HardFault） |
| `BASEPRI` | 关掉**优先级数值 ≥ 设定值**的中断 —— 比 PRIMASK 精细，RTOS 临界区常用 |
| `FAULTMASK` | 连 HardFault 都关（除 NMI） |
| `CONTROL` | 选择用 MSP 还是 PSP、特权级还是用户级 |

**两种模式与双栈（RTOS 的地基）**

- **Thread 模式**：跑普通代码，可用 MSP 或 PSP
- **Handler 模式**：跑异常/中断，**永远用 MSP**
- **双栈机制**：中断用 MSP，任务用 PSP —— 这就是为什么任务栈溢出不会立刻毁掉中断栈，也是上下文切换只换 SP 的原因

**CMSIS 封装（实际写代码用这些）**

```c
__disable_irq();       // PRIMASK = 1
__enable_irq();        // PRIMASK = 0
__get_MSP();  __set_MSP(x);
__get_PSP();  __set_PSP(x);
__get_CONTROL(); __set_CONTROL(x);
```

> 追问："RTOS 的临界区为什么要用 BASEPRI 而不是直接关中断？"
> → 直接关中断会把高优先级中断也一起挡掉，拉长实时响应；用 BASEPRI 只挡"低于某个优先级"的中断，**内核自己的 SysTick/PendSV 仍能响应**，切换不受影响。
